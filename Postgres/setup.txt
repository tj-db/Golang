ORACLE CLOUD SETUP CHECKLIST FOR setup.sh
==========================================

Key point: on Oracle Cloud, ports must be opened in TWO places:
the cloud network (Security List) and the instance's own firewall (iptables).
Missing either one makes certbot time out.


PART 1: CREATE THE INSTANCE
---------------------------

[ ] Image: Ubuntu 22.04 or 24.04. NOT Oracle Linux (it uses dnf, the script
    uses apt and will fail). The SSH user on Ubuntu images is "ubuntu".

[ ] Shape: both Always Free shapes work. ARM (Ampere A1) is fine because Go
    and Postgres support aarch64.

[ ] 1 GB AMD micro shape only: add swap before running, or "go build" can
    run out of memory:

        sudo fallocate -l 2G /swapfile
        sudo chmod 600 /swapfile
        sudo mkswap /swapfile
        sudo swapon /swapfile

[ ] Public IP: make sure the instance has a public IPv4 address. Convert it
    to a Reserved Public IP (Networking > IP management > Reserved public
    IPs) so it survives instance changes.


PART 2: LAYER 1, THE CLOUD NETWORK
----------------------------------

[ ] In the Oracle console go to:
    Networking > Virtual cloud networks > your VCN > your subnet >
    Security List (or the Network Security Group, if the instance uses one).

[ ] Add an Ingress Rule:
        Source CIDR:      0.0.0.0/0
        IP Protocol:      TCP
        Destination Port: 80
        Source Port:      leave blank

[ ] Add a second Ingress Rule, same as above but Destination Port: 443

[ ] Do NOT open 5432 (Postgres) or 8080 (Go server). Both listen locally only.

[ ] Leave the default egress rule (all traffic out). The script needs it.


PART 3: LAYER 2, THE INSTANCE FIREWALL
--------------------------------------

Oracle's Ubuntu images ship with iptables rules that reject everything except
SSH. Run these BEFORE the script:

        sudo iptables -I INPUT -p tcp --dport 80 -j ACCEPT
        sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT
        sudo netfilter-persistent save

[ ] Verify the two ACCEPT rules sit above the final REJECT line:

        sudo iptables -L INPUT -n --line-numbers

[ ] Do NOT enable ufw on top of this. It is inactive by default on these
    images, and mixing it with the iptables rules causes conflicts.


PART 4: DNS AND DOMAIN
----------------------

[ ] Create an A record for db.tjdb.online pointing at the reserved public IP.

[ ] Delete any old AAAA record pointing elsewhere (certbot may validate over
    IPv6).

[ ] Confirm it resolves to the right IP:

        dig +short db.tjdb.online

[ ] Cloudflare users: set the record to "DNS only" (grey cloud) until certbot
    succeeds. Check for an existing Cloudflare Tunnel too, since it would
    conflict with this setup.

[ ] Decide when to cut over from whatever serves the domain now.

[ ] Make sure nothing else on the new machine uses port 80 (Apache, an old
    nginx, Caddy).


PART 5: BEFORE YOU RUN THE SCRIPT
---------------------------------

[ ] Connect over SSH and start tmux, so a dropped connection does not kill
    the script half-finished:

        sudo apt install -y tmux
        tmux

[ ] Copy setup.sh to the server, make it executable, run it as your normal
    user (NOT with sudo):

        scp setup.sh ubuntu@YOUR.SERVER.IP:~/
        chmod +x setup.sh
        ./setup.sh

[ ] Have a password manager open. The script pauses to show you the admin
    token and database password.

[ ] Have a valid email ready. Certbot sends certificate expiry warnings there.

[ ] Outbound internet must work: apt mirrors, Go module downloads
    (proxy.golang.org, GitHub) and Let's Encrypt.

[ ] Go version: Ubuntu's packaged Go can be too old for the latest lib/pq.
    If "go mod tidy" or "go build" fails, install a newer Go and re-run.


PART 6: WHILE IT RUNS
---------------------

[ ] Copy the admin token and DB password when shown, then press Enter.

[ ] If certbot fails on Oracle, the cause is almost always one of the two
    firewall layers. Check the iptables rules first, then the Security List.
    Other causes: DNS not pointing at the server yet, or a Cloudflare proxy
    in front.


PART 7: AFTER IT FINISHES
-------------------------

[ ] Confirm the install worked. Expect 2 schemas, 12 functions, 12 routes:

        curl -sS -X POST https://db.tjdb.online/admin/map \
          -H "Authorization: Bearer YOUR_TOKEN" \
          -H "Content-Type: application/json" \
          -d '{}' | jq '.totals'

[ ] Save the admin token in a password manager, then delete the credentials
    file:

        rm ~/go-api-credentials.txt

[ ] Test certificate auto-renewal:

        sudo certbot renew --dry-run

[ ] Reboot once and re-run the map call. The iptables rules should survive
    thanks to "netfilter-persistent save":

        sudo reboot

[ ] Schedule pg_dump backups for the saved_data rows and store them OFF the
    instance. The script restores structure only, not rows. Oracle boot
    volume backups are a good second layer.

[ ] Free tier caveat: Oracle can reclaim Always Free instances that sit
    nearly idle for 7 days. Check the current policy in your account and
    consider upgrading to pay-as-you-go (free resources stay free) if this
    server matters.


OPTIONAL HARDENING
------------------

[ ] Restrict /admin/ to your own IP in nginx. The admin token can run
    arbitrary SQL, so it is the only thing between the internet and your
    database.

[ ] Keep SSH on key-only login (the default on Oracle images).


KNOWN LIMITATIONS
-----------------

- setup.sh is untested. Try it on a throwaway instance first.

- admin_list_functions holds an overwritten body, not your original.

- setup.sh goes stale when you add endpoints. After changes, call
  /admin/inspect-all and regenerate the embedded SQL blocks.

- Data rows in project_one.saved_data, roles beyond go-api, and grants
  beyond those in the script are not restored.
